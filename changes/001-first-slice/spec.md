# 首个记录助手夹具切片规格

行为依据是 Mono 工单 `DIANDI-001` 已确认的保存及按需反馈夹具验收。

## 需求

### REQ-RECORD-001 持久回执与幂等提交

可信调用方提交一条已确认的本人饮水记录。提交成功后，按原 owner 与客户端操作键能查回同一回执和条目版本。同键同负载复用结果，同键异负载返回冲突，独立操作键各自保存。

### REQ-RECORD-002 事务 Outbox 与离线恢复

正式条目、回执和一个稳定有序事件原子提交。客户端可以在 Memory 离线时完成保存和查回。恢复时使用原事件身份及负载摘要，分开确认接收和应用。

### REQ-RECORD-003 保存后按需反馈

提交回执可查后再决定是否反馈。默认仅保存，用户明确要求或 Agent 能根据本次已确认的容量补充比例时，按原操作和条目版本派发一次。首次决定可重载。自然结束与匹配的最终项才可发布，反馈失败或待核期间仍可读原保存回执。

### REQ-RECORD-004 待补输入与夹具身份边界

可信调用方已确认输入是本人饮水但缺少用量时，按原 owner 和客户端操作键持久保存原文，状态为待补。原键原文重试复用原操作，同键变更原文或改走正式提交返回冲突。待补输入没有正式条目、成功回执或 Outbox。调用方从已验证的测试身份绑定 owner，提交字段只能包含该入口允许的输入。

## 验收场景

### AC-RECORD-001 保存及重启读回

关联 REQ-RECORD-001，映射 Mono AC01。提交固定时间的 300 mL 饮水记录，重开原存储。查到同一回执及字段，新增各一条记录、回执及事件。主路径只返回正式提交回执。

### AC-RECORD-004 并发、精确重试及冲突

关联 REQ-RECORD-001，映射 Mono AC04。两个进程以原键并发提交，提交方在响应前退出。原键查回与重试共用原结果，同键改量冲突，新键可保存同内容的新条目。

### AC-RECORD-009 提交边界故障

关联 REQ-RECORD-002，映射 Mono AC09。事务写入后、提交前终止时三项均不持久，下一笔使用原序号。提交后、响应前终止时，重开库后保留同一回执及原事件身份和摘要。

### AC-RECORD-005 Memory 离线和响应丢失

关联 REQ-RECORD-002，映射 Mono AC05。离线仍完成保存与查询。重启后保持原事件，接收后丢响应时找回原 Memory 操作，已接收待应用时按原操作查询，最终只应用一次。

### AC-RECORD-002 按需反馈触发

关联 REQ-RECORD-003，映射 Mono AC02 并回归 AC01。默认分支没有反馈派发。明确请求和有效容量各能触发一次已保存记录的反馈。两种条件同时成立时按明确请求执行一次，重载仍复用原决定。

### AC-RECORD-007 反馈失败与回读恢复

关联 REQ-RECORD-003，映射 Mono AC07。测试模型错误、观察断开、最终项发布失败、非自然终态，以及保留 turn 后未确认或绑定失败。各变体保留原回执。可恢复结果只从原 turn 读回，其他分支保留失败或待核状态。

实际 router/runner 已接收首次 turn POST 但调用方未收到 turn ID 时，调用方重启后按原产品操作取回保存回执和反馈。它只查询原专用会话，依据持久化的操作键匹配唯一的原 turn，再查原最终项。查无、查询不可用、键不匹配或候选不唯一时保持待核。

### AC-RECORD-003 缺少用量时重启读回

关联 REQ-RECORD-004，映射 Mono AC03。独立进程接收“喝了水”后退出，重开同库可查到原操作、原文及缺用量状态。同键原文重试复用原结果，补前没有正式条目、成功回执和 Outbox，首笔后续正式提交仍使用序号 11。

### AC-RECORD-008 双用户夹具负例

关联 REQ-RECORD-004，覆盖 Mono AC08 的产品夹具子项。同租户另一用户查待补原文、操作、成功回执或正式条目，均得到与不存在相同的结果。客户端冒带 owner、tenant、目标条目 ID、grant 或正式来源声明时拒绝，请求无写入。各自使用相同客户端操作键时写入各自命名空间。真实产品登录和业务授权留待集成验收。
