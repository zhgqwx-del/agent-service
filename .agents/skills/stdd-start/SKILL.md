# 开始一项变更

1. 读 `AGENTS.md`、`docs/engineering.md` 和需求来源。沿能力规格、接口、代码和测试找出现状、目标及要保留的行为。列出影响实现的待定业务规则及对应 `REQ`、`AC`。
2. 若使用 Git，由 root 核对当前分支、未提交变更、开发基线和合入目标。默认沿用当前工作树并保留已有改动，远端同步和分支操作按仓库约定及本轮授权执行。参见 `docs/stdd/git-workflow.md`。
3. 复用已有变更目录。首个产品需求选定后，可继续完善 `changes/001-first-slice/`。新变更用 `python3 -B scripts/new_change.py <变更ID> '<标题>'`，加 `--roles` 生成四角色文档，复杂变更可另加 `--design`。
4. 默认先在 `tasks.md` 的「实施方案」写一份可评审的短方案。写清改哪些入口和组件、保留什么、关键取舍与风险，以及按哪些场景和命令验收。小改动可以用同样的内容记录在工单或 PR。复杂细节写入 `design.md`，任务里链接设计并保留实施顺序。
5. 查看 `docs/stdd/decisions-and-discussions.md`（如有）和项目已有记录。单次问题留在 `change.md`。跨角色、多轮或跨变更讨论按项目约定单列，缺省用 `docs/discussions/`。需要长期约定时先查 ADR 目录和既有决策，沿用项目指定路径或已有的 `docs/adr/`、`docs/decisions/`。现有记录优先复用。从 `change.md` 的「关联讨论与 ADR」链接相关文件或工单，标明本次影响及待确认项。
6. 先把方案和相关验收口径交给用户或项目负责人确认，记录确认来源或待决项。团队已有同范围的确认记录时直接沿用。支持规划模式的宿主可在此阶段使用规划模式。确认前推进规格、设计和准备工作，确认后交给 `stdd-delivery` 写测试与实现。
