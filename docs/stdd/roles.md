# 产品、设计、研发与测试协作

从[项目入口](project.md)打开具体变更。任一角色都可发起规格草稿，参与者按同一套编号确认各自负责的部分。

| 角色 | 需要确认的内容 | 文档入口 |
| --- | --- | --- |
| 产品 | 用户、可观察的目标、范围、业务边界和未决取舍 | [变更](templates/change.md) · [规格](templates/spec.md) |
| 设计 | 用户流程、可观察的交互状态、异常与可访问性 | [体验设计](templates/ux-design.md) |
| 研发 | 接口与依赖、兼容和数据约束、可验收的实现切片 | [技术设计](templates/design.md) · [任务](templates/tasks.md) |
| 测试 | 用例数据、预期、层级、执行命令和实际观察 | [验收计划](templates/test-plan.md) · [验收记录](templates/verification.md) |

## 交接一次变更

1. 用一个用户可观察的目标限定范围，在草稿写清输入、结果和待定规则。评审时逐项确认 `REQ` 与 `AC`。
2. 设计标出受影响的体验状态，研发确定稳定的验证入口，测试准备数据与边界用例。各角色文档用 ID 关联同一行为。已有同范围的方案和验收确认可以直接引用。
3. 按验收切片准备检查，再实现和复测。root 按[协作约定](../../AGENTS.md)统一执行验证，验收记录保留运行环境、实际结果和受测版本。
4. 交付后把实际已交付的行为同步到[现行规格](../../specs/README.md)。
